# 近づけて交換の設計

issue #693（手順 2「近づけて交換の本実装」）。試作は PR #700（#698）。
見た目の基準は `docs/design/nearby-exchange/`（D 案「入れ替わる（光のすきま）」）。

## 決めたこと

### 置き場所と既定

- 「QR・フレンド」タブの QR セクションに「近づける / マイQR / スキャン」の 3 セグメントを置く
- UWB に対応した iPhone では「近づける」を既定にし、QR は予備に回す
- UWB 非対応の iPhone では既定を「マイQR」にし、「近づける」を開くと理由と QR を出す
- iOS 以外（Android・Web）にはネイティブ実装が無いので、セグメント自体を出さない

### 何を送るか

- 相手へ送るのは **マイ QR に載せているのと同じ URL**（`?qt=` 対面交換トークン、qt が取れないときは `?ot=` オフライン交換トークン、`?mc=` ミニ名刺）
- 受け取った側は QR を読み取ったときと同じ処理に流す（`parseQrPayload` → `POST /me/friends`、通信できなければ交換キュー #681）
- サーバーと交換キューには手を入れていない。両方の端末がお互いを追加するが、friends の追加は冪等で、同日の再交換は 1 回の記録にまとまる（#662）

採らなかった案:

- **hello（発見時のあいさつ）にトークンを載せる** — 近くで「近づける」を開いているだけの人全員にトークンが渡ってしまう。トークンは 10cm まで近づけた相手 1 人だけに送る
- **近づけて交換専用の API・トークンを作る** — QR の対面トークンとオフライン交換トークンで成立条件（対面であること・期限）が既に満たせるため、増やさない

### 成立の条件

- 自分の端末が相手を 10cm 以内（`proximityLevel` の touch）と測った時点で、自分のデータを相手へ送る
- 相手から先にデータが届いた場合も、こちらのデータを送り返す。片方だけ受け取って終わらないようにするため
- 相手のデータが届いた時点で手元では成立とし、登録（API）の応答を待たずに演出を進める
- 6 秒以内に相手のデータが届かなければ、入れ替わりをやめて「もう一度近づけて」を出す

### 演出

- 送る（自分の名刺が上の端のすきまへ）→ 間（名刺形の紋が回る）→ 受け取る（相手の名刺が回りながら降りてくる）→ 着地、の 4 区間
- 「間」は最短 560ms。相手のデータが遅れればその分延びる
- 成立後は QR スキャンと同じ成立オーバーレイ・記録シート・お礼シート（`ExchangeResultLayer`）を出す。モックの「成立後」画面を別に作らず、QR と同じ導線（◯回目の表示・共通点を含む）に揃えた
- 相手の名刺ドキュメントは公開 API で取れないため、演出中の相手の名刺は名前とアイコンだけで描く
- 視差効果を減らす設定（Reduce Motion）では区間の長さを 0 にし、着地と成立だけを見せる

## 前提が変わったとき

- **相手の名刺のデザインを演出に出したい**: 公開スナップショット（`meishiSnapshotUrl`）を受け取り後に取得して差し替える。ただし電波の無い会場では取れないので、今の名前とアイコンの名刺はフォールバックとして残す
- **Android を出す**: Wi-Fi Aware（iOS 26 以降の iPhone とも通信できる）で発見・接続を作り直す。距離は UWB が無い機種が多いので、BLE の電波強度で近さを取る案を検討する（#693「使える API と制約」）
- **10cm の閾値・ハプティクスの帯を変える**: `lib/nearbyExchange/proximityLevel.ts` だけを変える。演出の育ち方（`approachProgress`）は 1m〜10cm の対数なので、閾値を変えたら式の端も合わせる
- **オフ会モード**（#693 手順 3）: `exchangeSession.ts` の「最も近い相手を主役にする」選び方を一覧表示に置き換え、送信のきっかけを距離からボタン操作に変える。送るデータと受け取り後の処理はそのまま使える
