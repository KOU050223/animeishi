# 14. アプリを持っていない相手の受け口（issue #664）

Issue: https://github.com/KOU050223/animeishi/issues/664
親: #637 テーマ A・大原則 2「一番の敵は、相手がアプリを持っていないこと」

## 目的

イベント会場で QR を渡した相手がアプリを持っていなくても、その場で名刺を
受け取れて、後からサインアップしたら交換が成立する受け口を作る。
実装は別 Issue に切り、本文書は体験の流れ・技術的な分岐・実装の分割を
決めるための設計メモ。

## 現状（2026-11-21 時点）

### QR に入る URL

- マイ QR（`apps/mobile/components/social/QrSection.tsx`）の値は
  `https://animeishi.uomi.dev/user/<uid>`。対面交換用の表示では
  `?qt=<exp>.<base64url(sig)>` を付ける（issue #417）
- `qt` は `GET /me/friends/qr-token` で発行する本人紐づきの短期トークン
  （TTL 300 秒、`CLERK_SECRET_KEY` で HMAC-SHA256 署名。
  `apps/api/src/features/friends/qrExchangeToken.ts`）
- 「リンクを共有」「リンクをコピー」は `qt` 無しの `shareUrl` を使う。
  一方、画面に表示する QR は `qt` 付きの `qrValue` を描画しており、
  「画像で保存」はそのカードをそのままキャプチャするため、**保存した
  QR 画像にも `qt` が含まれる**。つまり `qt` は対面表示だけでなく
  QR 画像の転送経路にも乗る（TTL 300 秒が実質の歯止め）

### アプリ未インストールの端末で開いたとき

1. OS のカメラで QR を読むと `animeishi.uomi.dev/user/<uid>?qt=...` が
   ブラウザで開く
2. Web 側の Worker（`apps/mobile/worker/index.ts`）が `/user/:uid` を
   振り分ける。クローラ UA には API の OGP 付き静的 HTML
   （`buildOgpHtml`）、ブラウザには SPA を返す
3. SPA の公開プロフィール（`apps/mobile/app/user/[uid].tsx`）は
   `GET /user/:uid` の JSON を表示する。内容はアバター・ユーザー名・
   bio・名言・ジャンル・SNS リンク・「いま見ている」吹き出し
4. 未サインインなら `GuestSignUpCta`（issue #562）が出て、
   `/(auth)/sign-up` へ誘導する。`savePendingReturn` が `/user/<uid>` を
   端末ローカルに保存し、登録・オンボーディング完了後に
   `useGuestCtaReturn` がそのプロフィールへ push で戻す
5. 戻ったプロフィールではフレンド申請ボタンが出る（申請→相手の承認制）

### 体験のギャップ

| あるべき流れ | 現状 |
| --- | --- |
| 読み取り → 名刺が開く | 公開プロフィールは開くが、**名刺そのものは出ない**。`GET /user/:uid` は `meishiSnapshotUrl`（#593 の公開スナップショット、幅 1280）を返しているのに、ページ側が表示していない |
| 名刺を保存する | 名刺画像が出ないので保存する手段がない。URL をブックマークするくらい |
| 後からサインアップ → 交換成立 | 登録後にプロフィールへ戻る仕組みはある。ただし `?qt=` は `profileReturnPath` の正規表現（`/user/{id}` のみ許可）で捨てられるし、そもそも Web のこの画面は `qt` を誰も読まない。戻った先でできるのは申請だけで、相手の承認待ちになる |
| 「双方向・同時」 | アプリなしの相手は「見る」側にしかなれない。`POST /me/friends` は認証必須で、たとえ `qt` を保持していてもサインアップ中に 300 秒の TTL が切れる。相手から自分へ名刺を返してもらう導線は無い |

### その他の制約・観察

- プロフィール非公開（`is_public = 0`）のユーザーの QR は `/user/:uid` が
  404 になり、受け取った側は「存在しないか、非公開です」しか見ない。
  会場で「渡したのに開けない」状態が起きうる
- OGP HTML の og:image はアバターで、名刺画像ではない。LINE 等で
  共有したとき名刺らしく見えない
- OGP HTML の「アプリで見る」リンクは `animeishi://user/<uid>` の
  カスタムスキーム。未インストールでは何も起きない（#220 で自動
  リダイレクトを試みないと決定済み）
- `qt` を読むのはアプリ内スキャナ（`useQrScanner` → `parseQrPayload`）
  だけ。アプリ所持者が OS のカメラで読んでも Web が開くだけで、
  即時成立にはならない（Universal Links が無いため）
- オンボーディングでは名刺の初回作成まで済む（好きな作品 → テンプレ
  → 名刺完成）。つまりサインアップを終えた相手は名刺を持った状態に
  なる

## あるべき流れ

```
QR を読む
  → ブラウザで名刺画像が開く（保存できる）
  → 「自分の名刺を作って交換する」でサインアップ
  → オンボーディングで自分の名刺ができる
  → 戻ってきたら交換が成立する（できれば即時、なければ申請）
```

「受け取った側から名刺を返してもらう」は、この流れの中で
「相手が名刺を作り → 交換が成立する → 自分の名刺帳に相手の名刺が入る」
として実現する。受け取り専用の別ページを新設せず、既存の
`/user/:uid` を名刺ファーストに改修する方向とする（ページを増やすと
OGP・ブロック・非公開の各判定を二重に持つことになるため）。

## 「双方向・同時」をアプリなしの相手でどう満たすか

即時成立の証跡は `qt` トークンだが、TTL 300 秒では
サインアップ＋オンボーディングをまたげない。選択肢は 3 つ。

### 案 A: `qt` を端末に保持し、登録後にそのまま `POST /me/friends` に渡す

`pendingReturn` と同じ要領で `qt` も保存し、`useGuestCtaReturn` の
戻り処理で交換成立を試みる。実装は最小だが、登録に数分かかる時点で
ほぼ確実に期限切れになり、申請フローへ落ちる。「対面即時」の体験を
期待させて裏切る導線になる。採るなら TTL の延長とセット（→ 案 B）。

### 案 B: `qt` の TTL を延ばす

「対面で画面に出した」証跡としての意味が薄れ、`qt` 付き URL が
SNS 等に流出したとき遠隔でも即時フレンドを成立できてしまう期間が
伸びる。申請→承認を迂回する権限を長く宙に浮かせる設計は避けたい。

### 案 C: 受け取り claim（推奨）

`qt` を「提示の証跡」として即座に「受け取り券」に引き換える。

1. `/user/:uid?qt=...` を開いたブラウザが、認証不要の
   `POST /exchange-claims`（仮）に `qt` と、クライアントがその場で
   生成したランダムな secret を渡す
2. API は `qt` を検証し、有効なら claim 行（claim ID・提示者
   userId・secret のハッシュ・有効期限・未消費フラグ）を
   D1 に記録して claim ID を返す。有効期限は時間〜日単位を想定
3. クライアントは claim ID と secret を端末ローカルに保存
   （`pendingReturn` と併置。URL・クエリには載せない）
4. サインアップ・オンボーディング後、認証付きの引き換え
   エンドポイント（または `POST /me/friends` の拡張）に
   claim ID と secret を渡して交換を成立させる

ポイントは `qt` の TTL を「QR を提示してから受け取り claim を
発行するまで」に閉じ込められること。登録フローの長さとは無関係に
対面証跡の寿命を 300 秒のまま保てる。

発行・引き換えの制御は次のとおり。

- **発行数の上限**: `qt` はステートレス署名なので、発行数を数える
  には D1 の claim 行が要る。同じ `qt`（提示者 + exp の組）から発行
  できる claim 数に上限を設ける。対面 1 対 1 が主用途だが、同じ
  QR を複数人が順に読むケース（画面を見せて複数人と交換、自分が
  保存した QR の再読み取り）を殺さないため 1 にはしない。上限値は
  実装 Issue で決める（数〜10 程度を想定）。加えて提示者あたりの
  時間あたり発行数に緩い上限を置き、流出した `qt` からの大量発行を
  抑える。上限を超えた発行要求は 429 で落とし、受け取った側は
  従来の申請フローへ流す
- **1 枚の QR を複数人が読んだ場合**: 上限内なら各読み取り側が
  自分の claim を発行でき、それぞれが引き換えて交換が成立する。
  これはオフ会的な使い方（#637 の未整理候補）とも整合する
- **消費は先着 1 回**: claim の引き換えは 1 回で消費する
  （used フラグ or 行の消去）。同じ claim を 2 アカウントで
  使い回せない
- **受取人の紐づけ**: claim 発行時に secret のハッシュを登録し、
  引き換え時に平文 secret の提示を求める。claim ID だけが漏れても
  secret が無ければ引き換えられず、これが「受け取った端末」の
  証明になる。未登録の受取人アカウントに事前紐づけすることは
  原理的にできないため、残存リスクとして「端末内ストレージから
  secret ごと抜き出した者は引き換えられる」ことを認める。
  bearer 情報を URL に載せない・端末ローカルだけに置く設計のため、
  漏洩経路は実質それに限られる

落ちた場合の出口として、claim が無い・期限切れのときは従来どおり
申請フローへ流す。つまりこの機構は「即時成立できたら儲けもの」の
上乗せであり、失敗しても行き止まりにならない。

副次的な利点として、すでに Web にサインイン済みの人（例: アプリ
所持者が OS カメラで読んだ場合や、Web 版利用者）が `?qt=` 付き URL を
開いたときは、その場で claim 発行→引き換えが完結し、Universal Links
無しでも即時成立になる。

### 採らない案

- Web 上でゲスト名刺を即席作成して返す: 「その場で双方向」は最も
  体験として近いが、アカウント無しの名刺データを公開 URL で持つ
  設計（モデレーション・有効期限・アカウントへの引き継ぎ）が重く、
  受け口の第 1 段としては過剰。オフ会モード候補（#637 の未整理
  候補）とあわせて別途検討する
- `animeishi://` への自動リダイレクト: #220 で未インストール時の
  挙動が不安定として不採用が決まっている

## Web で今すぐできること / ストア配信の基盤が揃った後にできること

| 今すぐできる（Web 側だけ） | 配信基盤が揃った後 |
| --- | --- |
| `/user/:uid` に名刺スナップショットを表示する（`meishiSnapshotUrl` は API が返却済み） | Universal Links（iOS。前提は Apple Developer 加入 #107 での Team ID と AASA 配信。#220） |
| 名刺画像の保存導線（ダウンロード・長押し保存） | Android App Links（前提はリリース署名の SHA-256 と `assetlinks.json` 配信。#220。Apple 加入とは無関係だが、署名はストア展開のタイミングでしか確定しない） |
| og:image を名刺スナップショットにする | App Clip（AASA の `appclips`、ネイティブターゲット、App Store Connect 設定が前提） |
| 受け取り claim（案 C）で登録後に交換を成立させる | Smart App Banner（App Store ID が必要） |
| 受け取り計測・CTA の文脈整備・非公開警告 | アプリ所持者が OS カメラで読んだときアプリへ直行し `qt` 付きで即時成立 |

App Clip について: Expo での App Clip はネイティブターゲットの追加が
要り、対応の実質的なハードルは Apple Developer Program 加入（#107）と
#220 の AASA 配信である。機能スコープは「名刺を表示し、フルアプリへ
誘導する」閲覧ビューアを第 1 段とし、Clip 内でのサインアップ・簡易
名刺作成までは後段に回すのが現実的。なお App Clip は iOS のみのため、
Android・その他では引き続き Web の受け口が主役になる（大原則 1 の
「QR はフォールバック」とも整合する）。

## 実装の分割案（1 項目 = 1 PR 程度）

Web で今すぐ始められるものから。括弧内は主な変更先。

- [ ] `/user/:uid` に名刺スナップショットを表示する
  （`apps/mobile/app/user/[uid].tsx`。`meishiSnapshotUrl` があれば
  ヘッダより先に名刺画像を出す。無い場合は現状のプロフィール表示）
- [ ] 名刺画像の保存導線を足す（Web はダウンロードリンク、
  ネイティブは共有シート。画像は公開配信済みの `meishiSnapshotUrl` を使う）
- [ ] OGP HTML の og:image を名刺スナップショットに差し替える
  （`apps/api/src/features/user/`。スナップショットが無い・非公開は
  現行のアバターを維持）
- [ ] 受け取り claim の API を設計・実装する
  （`POST /exchange-claims` で `qt` を検証し claim 行を D1 に記録、
  認証付きの引き換えエンドポイントで交換成立。
  `apps/api/src/features/friends/` 周辺。発行上限・TTL・secret
  照合・消費の扱いは案 C の制御どおり。具体値は Issue で決める）
- [ ] Web 側で `?qt=` を拾い claim に引き換え・保存する
  （`/user/:uid` または Worker。claim ID と secret を
  `pendingReturn` 同様ストレージに保持）
- [ ] サインアップ後の戻りで claim を使って交換を成立させる
  （`useGuestCtaReturn` の拡張。claim が無い・失敗したら従来の
  申請フローにフォールバック）
- [ ] 受け取り導線の計測を足す（名刺ページ閲覧・claim 発行・
  引き換え・申請フォールバックの各イベント）
- [x] QR 表示側でプロフィール非公開時に警告を出す
  （自分の QR を相手が開けないことに渡す側が気づけるようにする。
  `GET /me/profile` の応答に `isPublic` があるのでそれで判定する）
- [ ] GuestSignUpCta の文言・CTA を「名刺を受け取る」文脈に整える
  （上の仕組みが揃った後に効く導線改善）

配信基盤が揃った後（#220 本体。iOS は #107 の Apple Developer 加入、
Android はリリース署名の確定が前提）:

- [ ] Universal Links（iOS。`qt` をアプリ側へ引き渡せるかの確認を含む）
- [ ] Android App Links（assetlinks.json の配信。Apple 加入とは無関係）
- [ ] App Clip ターゲットの追加（名刺閲覧＋本体誘導の第 1 段）
- [ ] Smart App Banner（App Store 公開後）

## 前提が変わったとき（What if）

- **#427 の「名刺ドキュメントは端末から出ない」決定を変えたとき**:
  サーバーにドキュメントがあるなら動的レンダリングの名刺を出せるが、
  現行の静的スナップショット（#593）が公開表現の正本である以上、
  受け取り画面もスナップショットで揃えるのが筋。変更不要の見通し
- **claim 機構を後から止めたいとき**: claim API を消しても
  `?qt=` 無しの URL は従来どおり公開プロフィールを開き、申請フローへ
  落ちるだけなので退化しない
- **App Clip が本命の受け口になったとき**: iOS では Web 受け取りが
  フォールバックに回るが、Android と App Clip 非対応経路（SNS 内
  ブラウザ等）は Web が残る。Web 側の改修は無駄にならない
- **名刺に公開範囲の段階（#658 の SNS リンク等）が乗ったとき**:
  スナップショット画像は生成時点で固定されるため、公開範囲の細かい
  出し分けは画像に反映できない。「公開名刺 1 枚」の割り切りを
  続けるかは #658 の決着と合わせて再確認する

## 判断が必要な点（Issue 起票時にオーナー確認）

- 非公開プロフィールのユーザーの QR を受け取った側に何を見せるか。
  案: (a) 現状どおり 404 のまま＋渡す側に警告、(b) `qt` 付き URL で
  名刺スナップショットだけ一時的に見せる（トークンを公開の代替証跡に
  するが、URL 流出リスクと TTL の兼ね合いを要検討）
- 交換成立の即時性をどこまで求めるか。案 C の claim 機構は新しい
  API と D1 の claim テーブルを要する。「登録後は
  申請フローで十分」と割り切る選択もあり、その場合は claim 関連の
  項目を落とせる
- claim 機構を採る場合の具体値。1 つの `qt` からの発行上限・
  提示者あたりの時間あたり上限・claim の TTL。会場で同じ QR を
  何人が読みうるか（オフ会モードとの整合）を踏まえて決める
